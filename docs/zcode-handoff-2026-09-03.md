# 给 zcode 的交接：铜镜翻页问题与修复

日期：2026-09-03

**结论：主要问题在翻页和手势代码，3D 也有不必要的渲染开销。保留 3D 后已解决本次翻页问题，不需要因此改成纯平面页面。**

修复已提交到 GitHub `main` 并部署到 [GitHub Pages](https://cfyofjackie.github.io/ancient-mirrors-museum/?v=b8f4a18)。用户已用手机检查线上版本，反馈这次没有问题；首次打开铜镜仍需要加载。

## 1. 查到了什么，如何解决

| 问题 | 解决办法 |
| --- | --- |
| **翻页有可见的瞬移。** 旧页只移动约半屏，底部文字还看得见，就切换内容并跳到屏幕另一侧，因此看起来“卡一下”。 | 镜子和文字共用一套过渡：先滑动并淡出，完全不可见时换内容，新镜准备好后再进入。 |
| **快速短滑没有响应，箭头按钮也点不到。** 手势只判断距离，按钮又继承了禁止点击的样式。 | 加入滑动速度判断，恢复按钮点击；同时处理取消、多指、连续反向和动画中途再次拖动。 |
| **镜子与文字运动不同步。** 外层整页在滑动，镜子内部还另做一次升起动画。 | 删除内部升起动画，让镜子和介绍文字一起移动。 |
| **静止时 3D 仍不停绘制。** 手机持续承担无必要的渲染工作。 | 在已有渲染器常驻的基础上改为按需绘制：翻面、倾斜、换素材、尺寸变化时才画，静止后停止。 |
| **贴图重复创建、上传。** 缓存只记住已加载完成的图，加载中的相同请求无法合并。 | 缓存加载中的 Promise；当前镜优先，后续镜分批准备，避免集中初始化和重复上传。 |
| **法线贴图下载了却没用上。** 用来表现表面凹凸的图片没有绑定到材质。 | 补全 `normalMap` 绑定，让已有资源实际参与渲染。这也是一个视觉与资源使用错误。 |

另外补齐了 WebGL 不可用或素材失败时的平面回退交互，以及开发模式重复挂载时的资源清理。

## 2. 是怎么排查出来的

1. **先核对文档、代码和线上版本。** 发现部分交接说明与实际代码不一致，例如文档写了速度判定，代码却只判断距离；确认本地复现的是线上同一版代码。
2. **重复触发，记录实际位置。** 在桌面和手机尺寸页面连续翻页 8 次，逐帧记录位置、可见范围和内容变化。旧版 8 次都出现可见瞬移，手机尺寸下单次跳变约 928 像素。
3. **每次只改一个因素做对照。** 暂停 3D 绘制，断跳仍是 8/8；仅让旧页完全离开视野后再切换，断跳变为 0/8。这说明主要断跳来自翻页逻辑，不能全部归咎于 3D 或 GitHub 网络。最终修复采用淡出后换内容，没有直接照搬实验中的超长位移。
4. **分别检查输入和资源。** 回放 50px／80ms 的快速短滑，发现旧版全部不翻页；检查按钮实际命中对象，发现点击被穿透。再统计贴图上传和绘制次数，并检查材质，定位重复工作及缺失的法线绑定。
5. **修改后用相同方法复测，再让用户真机验收。** 构建和 11 项交互检查通过，覆盖快速反向、取消、翻面、资料卡及异常回退。随后发布线上，检查四朝循环与文字显示，用户手机复测确认正常。

同一台电脑、同样画布条件下，8 次翻页的可见断跳从 **8 次降到 0 次**；测试期间 3D 绘制从 **1622 次降到 8 次**；8 张贴图的初始上传从 **10 次降到 8 次**。这些是对照测试数据，不是手机实测帧率。

## 3. 目前还要知道的两件事

**首次打开仍会加载。** 首次显示需要下载、解码图片，并准备 GPU 贴图和着色器；现在会等首镜准备好再显示。重复上传已消除，但首次准备仍有成本，和资源加载完后的翻页断跳是两个问题。目前没有测出各阶段耗时占比；如果继续优化，先测首屏耗时，再考虑加载占位和贴图体积。

**手机文字曾短暂出现在屏幕外，但原因未确证。** 用户用 Firefox 重新打开、刷新后恢复正常。真机采集的可视高度约 755px，文字底部约 735px，确实在屏幕内。这次没有修改正式布局，也不能认定已经修复了某个 Firefox 或缓存缺陷；若再出现，应先采集异常时的尺寸。

## 核心结论

**至少一部分“卡顿”是翻页逻辑制造的视觉断跳，即使没有明显帧率停顿也必然发生。** 同时还有手势忽略、按钮点不到、首次纹理初始化集中执行等问题。当前证据不足以断言小米真机上没有额外的 GPU 掉帧或网络影响。

### 1. 旧页没有离屏，就瞬间搬到另一侧（确定，最高优先级）

位置：`src/App.tsx:42–51`。

当前顺序是：150ms 内移动 0.55 个视口高度 → `setIndex()` → `dragY.jump(-out)` → 380ms 从另一侧进入。镜子和所有底部文字在同一个 `.page` 容器中，没有淡出遮蔽。

在 390×844 的视口，上滑终点约 -464px，紧接着变为 +464px。逐帧实测跳变约 927–928px；跳变前旧页底部还在屏幕的 y≈360px。内容在用户看得见时消失、换朝代并瞬移，所以会感觉“断一下”。下滑方向同样只退出半屏，存在同类可见内容替换问题。

用正式构建连续切换八次，八次全部复现。只改变退出距离，使旧页完全离屏后再换，八次断跳检查均通过。**1.1 屏只是单变量诊断实验，尚不是建议直接交付的完整动画设计。**

### 2. 快速短滑会被忽略，按钮也无法兜底（确定）

位置：`src/App.tsx:82–91`；`src/index.css:170`、`:230`。

- 手势只看最终距离是否超过 70px，没有计算速度。正式构建的 pointer 回放中，50px / 80ms 的快速短滑连续八次均回弹、零次翻页；100px / 80ms 对照可完成八次切换。快速但短的甩动会显得“不跟手”。PROGRESS 仍记录“位移 70px 或速度 350px/s”，与实现不符。
- `.mirror-stage` 设置了 `pointer-events: none`，仅 canvas、热点恢复了点击；`.stage-nav` / `.nav-btn` 没有恢复。浏览器实测两按钮的 computed `pointer-events` 均为 `none`，中心坐标命中 `.page`，不是按钮。视觉上有 ↑↓，实际用户点击被穿透。
- `pointercancel` 被当成 `pointerup`；多指身份、非主指针、取消恢复没有独立处理。这是代码层面的边界风险，本次没有模拟所有真机触摸取消情形。

### 3. 同时保留两套位移动画（确定存在，属于次要因素）

位置：`src/components/Mirror3D.tsx:243–248`、`:291–293`。

App 已经负责整页滑动；换素材时 `applyArt()` 又把铜镜局部 y 重设为 -0.3，然后在 450ms 内升到 0。于是镜子与文字只共享外层位移，镜子内部仍额外运动。HANDOFF 说旧 3D 换展动画已删，实际仍保留了这段升起。

取消升起后，主要断跳仍八次全出现，因此它不是主因，但会影响动作同步和观感。翻面中换朝代还会先把 `flipped` 设为 false；统一过渡时也应处理这条状态链。

### 4. 首屏纹理初始化有真实开销，且存在重复工作（确定开销，手机影响幅度待测）

位置：`src/components/Mirror3D.tsx:124–153`、`:227–230`。

八张 1024×1024 运行贴图合计约 3.06MB。首次进入同时开始加载四个朝代；当前朝代的 `applyArt()` 又调用同一加载函数。缓存只保存已经完成的 Texture，没有缓存加载中的 Promise。

在取消开发双挂载的计时实验中，八张图触发了 **10 次 `initTexture`**，单次中位约 30ms、最大约 35ms。HTTP 层可合并相同图片请求，但仍创建和上传了重复 Texture。这个同步工作会集中在初次加载阶段，而不是平均分散到后面。

正式构建另记录到一次 76ms 启动长任务；未做调用栈归因，因此不能把这 76ms 全部算到某个函数上。热身后翻页的八轮测试没有新增网络请求，计时版也没有新增 `initTexture`。

### 5. 凹凸贴图加载了，却没有用到材质（确定的资源与视觉错误）

位置：`src/components/Mirror3D.tsx:218–225`。

normal 分支仅赋值 `tex.normal = t`，漏了 `mats.back.normalMap = t`。材质在纹理加载前以 null 创建；正常主页面不会再切换 mode 重建材质，所以当前常规流程中的 `mats.back.normalMap` 一直为空。运行探针确认 `normalMap: false`。

四张法线贴图合计 2,012,722 字节（约 2.01MB），仍被下载和上传 GPU，却没有参与表面凹凸。按 RGBA8 + 完整 mipmap 估算，它们约占 21.3MiB 纹理存储，具体驱动分配未测。修复绑定会恢复原计划的凹凸效果，也会增加实际着色工作量，需要一起做移动端预算，不能只补赋值就宣称性能已修好。

## 实验记录

全部实验在同一台 Windows 电脑的可见 Chromium 页面完成。移动尺寸实验是 390×844；开发计时实验另设画布 DPR=2。它们**不模拟小米 13 的 CPU/GPU**。生产实验直接使用未修改的 dist 主程序，只附加 DOM、rAF、Long Tasks 观察脚本。

| 实验 | 完成切换 | 可见内容断跳 | 说明 |
| --- | ---: | ---: | --- |
| 原始正式构建，手机尺寸 | 8/8 | 8/8 | 约 927–928px 瞬移；帧间隔 p95 6.1ms |
| 原始正式构建，桌面 1280×800 | 8/8 | 8/8 | 约 879px 瞬移；旧页底部仍在 y≈341px；帧间隔 p95 6.2ms |
| 原始开发构建，手机尺寸，DPR=2 | 8/8 | 8/8 | 计时版换几何最大约 2.9ms |
| 仅停止 3D 绘制 | 8/8 | 8/8 | 测量期 render 调用为 0，断跳依旧 |
| 仅取消局部升起 | 8/8 | 8/8 | 改观感不能消除主故障 |
| 仅让旧页完全离屏 | 8/8 | 0/8 | 单变量证明可见时瞬移是主因 |
| 正式构建，50px / 80ms 短滑 | 0/8 | 不适用 | 全部回弹，未触发切换 |
| 正式构建，100px / 80ms 长滑 | 8/8 | 8/8 | 输入被接受后仍走有断跳的过渡 |

上述热身后实验均未记录超过 50ms 的 rAF 帧间隔；这不代表 GPU 每帧实际呈现都达标。JS `renderer.render()` 调用耗时也不是 GPU 执行时长。这里只能排除“这台电脑上每次翻页都发生很长 JS 阻塞”的解释，不能排除手机上额外掉帧。

原始逐帧 JSON 保存在 `scripts/diagnostics/results/`。工具用法见 `scripts/diagnostics/README.md`。已执行的判定命令：

```text
node scripts/diagnostics/check.mjs baseline
FAIL: visible content teleports during page switch        (exit 1)

node scripts/diagnostics/check.mjs full-exit
PASS: no visible content teleport                         (exit 0)
```

## 不应混为一谈的事项

- **GitHub Pages 的网络速度**可能影响首屏。此处本地静态正式构建、资源已加载完、翻页不再发请求时仍复现断跳，因此网络无法解释全部翻页问题。
- **渲染器反复重建的旧问题**在当前切换路径已改为常驻。计时版热切换没有再次上传贴图，程序数量也未随切换增长。不要按旧交接结论重复修同一个问题。
- **3D 仍每帧不停绘制**，空闲也不停止；DPR 最高 2、最大各向异性采样、全屏变色和 SVG 颗粒也是移动端应检查的预算项。但本次不能把它们写成已经证实的真机掉帧根因。
- **包体约 32.4MB，明显超过文档自设 5MB 预算。** publicDir 把未引用的原始 PNG、馆藏大 JPG 和中间高度图也复制进 dist。它们影响部署/未来离线包体积；浏览器不会因为它们存在于 dist 就自动全部下载，不能把 32.4MB 当成首屏下载量。
- WebGL 回退分支使用 `.mirror-flip`，当前点击翻面处理只识别 `.mirror-3d-wrap`，回退分支也没有热点层；这属于静态检查发现的功能缺口，非本次主要卡顿结论。

## 建议修复顺序

1. **先统一翻页状态和动画进度。** 让文案与铜镜共享一套过渡；内容仍可见时不瞬移、不换素材。正确处理拖拽中断、翻面中切换、快速反向操作。单纯改时长、缓动或把 0.55 改大都不足以完成整体手感设计。
2. **恢复按钮命中，加入速度判定与取消恢复。** 先让每次有效输入有可预期的结果，再调视觉。
3. **解决首次加载重复工作。** 缓存进行中的 Promise；当前镜优先，分批准备后续资源；处理加载失败、过期请求和纹理生命周期。镜体几何可以按轮廓缓存，但当前桌面计时表明它不是第一优先级。
4. **修法线绑定并做真机预算。** 在实际手机测首屏、静止、翻页和翻面四种状态；再决定纹理分辨率、DPR、各向异性和空闲按需渲染策略。
5. **清理产物与文档。** 分离源素材和运行素材，更新 README 的旧技术栈、占位图说明，以及 PROGRESS/HANDOFF 的动画、手势和体积描述。

本次新增的是诊断脚本、原始测量记录和报告；业务源码保持仓库版本，远端部署未变更。当前最有价值的下一步是按上述顺序实施修复，再用这组断跳检查与真机录制验证结果。
